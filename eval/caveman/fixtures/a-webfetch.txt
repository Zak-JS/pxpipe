The short answer is that Node.js worker threads became genuinely practical for CPU-bound work in Node 12.11.0, when the worker_threads module was unflagged, but the ergonomics most teams rely on today arrived later. SharedArrayBuffer transfer stabilized in 14.5.0, and the structuredClone global that makes message passing painless did not land until 17.0.0. If you are still supporting Node 16.20.2 (the last 16.x release, end-of-life since 2023-09-11), you can use worker threads freely but should avoid the newer postMessage transfer list shorthand.

The performance picture is more nuanced than most blog posts suggest. Spawning a worker costs roughly 10-15 ms and about 6 MB of resident memory per thread on Linux, measured on Node 20.11.1 with the default 4 MB stack size. That overhead means workers only pay off when a task takes longer than about 50 ms of pure computation. For anything shorter, the serialization cost of moving data across the thread boundary eats the gain. The piscina library (currently at 4.4.0, maintained by the same people who wrote the underlying module) amortizes spawn cost with a pool, and in the maintainers' own benchmarks a warmed pool handles 125,000 trivial tasks per second, versus roughly 900 per second if you naively spawn a fresh worker each time. That is a 138x difference, and it is the single most common mistake in production deployments.

Data transfer deserves its own paragraph. A postMessage call clones its payload by default using the structured clone algorithm, which for a 100 MB Buffer takes around 40 ms. If you instead transfer the underlying ArrayBuffer by listing it in the transfer array, the handoff is under 0.1 ms because ownership moves rather than bytes. The catch is that the sending side loses access; reading a transferred buffer afterward throws a TypeError. SharedArrayBuffer avoids both costs but requires Atomics for coordination, and the Atomics.wait call blocks the thread, so it is forbidden on the main thread in browsers and strongly discouraged on the Node main thread.

For scheduling, the event loop and the worker pool interact badly if you get the pool size wrong. The rule of thumb from the libuv documentation is to size CPU-bound pools at os.availableParallelism() minus one, leaving a core for the event loop. Oversubscribing by even 2x can raise p99 latency by 300% under load, because the OS scheduler starts preempting workers mid-task. Note that os.availableParallelism() (added in 18.14.0) respects cgroup CPU limits inside containers, while the older os.cpus().length does not, which is why containerized deployments sized with the old API routinely oversubscribe by 4x or more on shared Kubernetes nodes.

Finally, error handling. An uncaught exception inside a worker emits an error event on the Worker object and terminates that worker with exit code 1; it does not crash the parent. But an uncaught exception in a message handler on the parent side will crash the whole process as usual. The canonical reference is the official documentation at https://nodejs.org/api/worker_threads.html, and the piscina docs at https://github.com/piscinajs/piscina cover pool sizing in detail. For a deep dive into the transfer semantics, the HTML spec section on structured cloning at https://html.spec.whatwg.org/multipage/structured-data.html is the authoritative source, dry as it is.
